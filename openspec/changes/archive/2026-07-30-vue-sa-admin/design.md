## Context

See proposal.md for motivation. The current `sa_admin` front-end is a set of vanilla JS classes extending a custom `Component` base class (`component.js`). These classes manually build DOM via `innerHTML`, track event listeners, and wire up cross-component communication through `CustomEvent` dispatching. The data layer is Backbone 1.0.0 loaded as a global script (`Shareabouts.PlaceCollection`, `Shareabouts.PlaceModel`), with jQuery for AJAX.

Django serves two admin pages via the `shareabouts_loggedin` decorator:
- `/admin/` — dashboard (table + map + filters)
- `/admin/detail/<id>/` — place detail (form + map + undo/redo)

Each page injects config and user data into `window.Shareabouts` via Django template tags. The existing Grunt build is for `sa_web` only; `sa_admin` currently uses zero-build native ESM.

## Goals / Non-Goals

**Goals:**
- Replace all custom `Component` JS with Vue 3 SFCs while preserving identical end-user functionality
- Establish Vite as the `sa_admin` build tool with Django integration via `django-vite`
- Bridge Backbone models/collections into Vue's reactivity system as the single data source of truth
- Maintain Django-side auth and routing unchanged
- Lay groundwork for flavor-based extensibility via Vue slots and provide/inject

**Non-Goals:**
- Modernizing Backbone itself (no ESM, no `fetch` API replacement)
- Migrating `sa_web` to Vue (remains on Backbone views)
- Replacing jQuery or Underscore globally
- Building a complete flavor extension API (slots will be added incrementally)
- Client-side routing via Vue Router (Django handles routing)

## Decisions

### Decision 1: Vue 3 SFCs with Vite (over Web Components or zero-build Vue)

**Choice**: Vue 3 Single-File Components compiled by Vite.

**Alternatives considered**:
- **Web Components (Lit/vanilla)**: Evaluated for vanilla JS simplicity. Rejected because `sa_admin` needs reactive data propagation across a complex component tree (table ↔ map ↔ filters ↔ counts), undo/redo state, and conditional/loop rendering — all of which require re-implementing what Vue provides natively. Web Components' `<slot>` mechanism lacks template-level logic (`v-for`, `v-if`).
- **Zero-build Vue via `vue.esm-browser.js`**: Would avoid a build step but loses SFC support, scoped styles, and HMR. The string-template syntax is harder to read and maintain than SFCs.
- **Preact + htm**: Lightweight VDOM alternative. Less ecosystem/tooling support, and tagged template literals are less ergonomic than SFC `<template>` blocks for complex admin layouts.

**Rationale**: Vue SFCs provide the best balance of encapsulation, readability, tooling (devtools, HMR), and ecosystem familiarity for contributors. Vite is already the default Vue build tool and adds minimal configuration.

### Decision 2: Multi-page entry points (over SPA with Vue Router)

**Choice**: Separate Vite entry points for each Django-rendered page (dashboard, place detail).

**Alternatives considered**:
- **SPA with Vue Router**: Would enable client-side navigation and shared state across pages. Rejected because: (a) there are only 2 routes; (b) place detail pages must open in separate browser tabs so users can have multiple open simultaneously; (c) Django's `shareabouts_loggedin` decorator handles auth per-request, which is simpler to preserve with server-rendered pages.

**Rationale**: Multi-page avoids complexity without meaningful loss. Each page is a self-contained Vue app that mounts into a Django-rendered shell. Adding Vue Router later is a straightforward migration if the page count grows.

### Decision 3: Vite project inside `src/sa_admin/` (over top-level)

**Choice**: Place `vite.config.js`, `package.json`, and Vue source inside `src/sa_admin/`.

**Alternatives considered**:
- **Top-level `sa_admin_ui/` directory**: Cleaner separation for JS developers but requires `STATICFILES_DIRS` configuration and splits the Django app across two locations.

**Rationale**: Keeping the Vite project co-located with the Django app means `collectstatic` finds built files automatically via `AppDirectoriesFinder` (output to `static/sa_admin/dist/`). All of `sa_admin` lives in one directory. `vite.config.js` sets `base: '/static/sa_admin/dist/'` and `server.cors: true`, while Django's `DJANGO_VITE` settings include `'static_url_prefix': 'sa_admin/dist'` so dev server asset URLs generated by `django-vite` match Vite's base path and pass CORS checks.

### Decision 4: Backbone globals accessed via `window` (over npm import)

**Choice**: The Vue app references `window.Backbone`, `window.Shareabouts`, `window.$`, and `window._` as externals.

**Alternatives considered**:
- **Install Backbone via npm and import in Vite**: Would enable tree-shaking and proper module resolution, but Backbone 1.0.0 has no ESM build and depends on jQuery/Underscore as globals. The `sa_web` app also depends on these exact globals. Modernizing this is out of scope.

**Rationale**: The Django shell template loads Backbone and its dependencies as `<script>` tags before the Vue app's `<script type="module">` executes (modules are deferred). The Vue app accesses them via `window`. Vite's `build.rollupOptions.external` marks them as external so the bundler does not try to resolve them.

### Decision 5: `shallowRef` array copy bridge (over deep reactivity wrapping)

**Choice**: Backbone models/collections are wrapped in Vue's `shallowRef`. For collections (`useBackboneCollection.js`), the composable maintains a shallow array copy `[...collection.models]`. On Backbone events (`change`, `add`, `remove`, `reset`, `sync`), a new array copy `modelsRef.value = [...collection.models]` is assigned.

**Alternatives considered**:
- **Deep `reactive()` wrapping**: Would make every attribute deeply reactive but conflicts with Backbone's internal state management. Backbone models use `attributes` hash and `changed` tracking — wrapping them in a Proxy would interfere with `model.set()`, `model.get()`, and change detection.
- **`triggerRef` without array copy**: Keeping a reference to `collection.models` and calling `triggerRef` fails for Vue 3 array watchers (`watch(() => props.places)`) because `collection.models` is mutated in-place by Backbone, meaning `newValue === oldValue` and Vue skips watcher callbacks.
- **Data duplication**: Copy Backbone data into Vue reactive state. Rejected because it creates two sources of truth and requires bidirectional sync logic.

**Rationale**: `shallowRef` with array copy re-assignment treats Backbone models as opaque while providing Vue's reactivity system with distinct array reference changes (`newValue !== oldValue`). Vue components and watchers re-render automatically when Backbone fetches data asynchronously.

### Decision 6: Bootstrap data via `window.__SA_BOOTSTRAP__` (over API endpoint)

**Choice**: Django template injects config, user, dataset, and token data into a global `window.__SA_BOOTSTRAP__` object. A `useBootstrap()` composable provides typed access.

**Alternatives considered**:
- **Dedicated API endpoint**: Would decouple the Vue app from Django templates entirely, but adds a network round-trip, requires auth token management in the client, and the data is already available at template render time.

**Rationale**: This preserves the current injection pattern (previously `window.Shareabouts.Config` and `window.Shareabouts.bootstrapped`) with a cleaner namespace. No additional API calls needed.

## Risks / Trade-offs

- **[Build step complexity]** → Mitigated by Vite's minimal config defaults and `django-vite` handling the dev/prod manifest switching. The `sa_web` Grunt build is unaffected.
- **[Backbone 1.0.0 is ancient]** → The shallowRef bridge is deliberately version-agnostic. It depends only on `.on()` / `.off()` / `.get()` / `.models`, which have been stable across all Backbone versions. Upgrading Backbone later will not break the bridge.
- **[Flavor extensibility regression during migration]** → During the initial conversion, per-deployment admin customization via Django template overrides will be replaced by Vue slots/provide-inject. Full coverage of all extension points will be layered in iteratively. Deployments that currently override admin templates will need to adapt.
- **[Global script load order]** → Backbone, `models.js`, and `window.__SA_BOOTSTRAP__` must load before the Vue app mounts. To achieve this, `{% block vite_assets %}` is placed at the bottom of `base.html` after Backbone dependencies and bootstrap data initialization scripts.
- **[Browser module compatibility]** → `csv-stringify` must be imported via `csv-stringify/browser/esm/sync` to avoid Node.js `Buffer` global reference errors in the browser.

## Migration Plan

1. **Add Vite + Vue + django-vite** to `src/sa_admin/` and Django settings. Verify dev server HMR and production build both work with a minimal "hello world" Vue component.
2. **Port components bottom-up**: widgets → filters → table/map → dashboard/detail. Each component can be developed and tested against the existing Backbone data layer.
3. **Replace Django templates** with thin shells that mount the Vue apps. Remove the old `static/sa_admin/js/` files.
4. **Update deployment pipeline** (e.g. `Dockerfile`) to run `cd src/sa_admin && npm ci && npm run build` before `collectstatic`.
5. **Update documentation** (`doc/README.md`) to clarify that `cd src/sa_admin && npm run dev` is needed for local development of the admin UI.
6. **Rollback**: Git revert. The old JS files and templates can be restored since Backbone models/collections are unchanged.
